## Acceptance and evidence boundaries

The application proof runs Better Auth and real local D1 in workerd. Only the external provider transport is substituted. Actual Polar Sandbox checkout was separately completed by the developer, and the resulting active subscription was read through authenticated MCP. Its sanitized response is replayed through the real adapter and D1 isolation tests. This is combined provider observation plus transport replay, not a deployed end-to-end application checkout or a live-money transaction.

## Identity and retention contract

Production checkout must start from a backend-created intent for the canonical Better Auth user, designated payer and current household. Polar `customer.external_id` must identify that person. A public checkout link and email matching are only fixture tools and must not become the authenticated production checkout flow.

The immutable reconciliation tuple is environment + organization + subscription, with intent + opaque payer + household + customer + product IDs. Verified entitlement stores paid-through time. Profile deletion clears the user reference without transferring that tuple. Retention of these billing references needs O02's basis, scope, access control and duration before real charges.

This proof accepts an active, unexpired verified subscription to establish/refresh access. It does not implement immediate revocation of earlier grants on refunds, scheduled cancellation, grace policy, webhook validation, out-of-order lifecycle reconciliation, deletion-time provider cancellation, production checkout or prevention of a second charge. T29/T30/T34/T48 own those obligations. A single-entitlement constraint is not proof that the provider cannot charge twice.

## Provider observations and reproduction boundary

[Sanitized provider report](t08-polar-sandbox.json) records the subscription tuple and cleanup. [Recorded response fixture](../../apps/api/tests/billing/fixtures/polar-sandbox-subscription.json) retains only fields consumed by the adapter. The fixture clock is pinned to capture time so the historical evidence does not fail merely because the original subscription period expires.

Renaming the synthetic Polar customer preserved its ID and personal `external_id`. An attempted reassignment to `t08-payer-20261015-b` returned `PolarRequestValidationError`: `Customer external ID cannot be updated.` A subsequent subscription read still resolved the original payer. No provider customer was deleted: application-profile deletion and retained references are exercised by D1, and deletion-time cancellation remains T34's responsibility.

The replay seeds a synthetic Better Auth account with the observed external ID, signs in through OTP with in-memory mail, prepares a D1 household intent and reconstructs the recorded fixture intent ID. It then passes the unchanged observed subscription fields through `createPolarProvider` into `restore`. Household A gains access; payer B and moving payer A to household B cannot claim it. Reconstructing this fixture is not evidence that a production Checkout API route already exists. T30 must create checkout sessions from a real stored intent before payment.
