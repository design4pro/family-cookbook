## Behavior and evidence

| Requirement | Implemented behavior | Evidence |
| --- | --- | --- |
| One private book, one active membership | The household row is the single cookbook boundary. A D1 batch creates the household, membership and separate billing designation. The existing unique member constraint and conditional inserts prevent concurrent creation/joining of two households. | Competing creation and two-household invitation tests; authenticated creation ignores client-supplied identity/role fields. |
| Separate administrator and payer | Creator initially holds both roles; administration is stored on the household, payer designation in the existing billing table. Membership removal does not change payer designation, billing binding or entitlement. | Creation assertions and removal of a designated payer; no provider mutation occurs. |
| Up to five members | Acceptance checks capacity in the atomic insertion; an additional database trigger enforces the bound. Invitations do not reserve seats. | Six competing invitees obtain only four remaining places; one owner plus four members remain. |
| Email-bound, expiring, single-use invitations | 256-bit random bearer tokens, only SHA-256 hashes persisted. Verified session email must match the normalized invitation address. Acceptance and consumption commit together. Administrator can revoke a pending invitation. | Wrong user, unverified email, expired token, unknown token, duplicate acceptance and revocation tests. |
| Administrator authority | Creation of invitations and removal of other members require current administrative membership. Old issuers cannot admit members after losing that role. | Non-administrator and already-removed-session denial tests; SQL predicates recheck authority inside writes. |
| Leave/removal revokes access | Removing membership atomically cancels/fences pending or running imports and releases reservations. Existing shopping writes recheck membership. Private-read guard checks membership before reading and again before returning an asynchronous result. | Actual D1 shopping and job calls reject removed users; a previously claimed job cannot publish even after rejoin. Private-read callbacks are not called after removal; a response fetched during removal is suppressed. |
| Preserve account and content | Membership deletion does not delete the user, private sources or contribution data, and does not cancel a subscription. | Same session still reads its account but sees no household; source row and R2 object remain intact; billing designation remains unchanged. |
| Administrator continuity | An administrator with other members cannot leave until handover. Last-member departure closes the household and revokes outstanding invitations. | Server and UI tests cover refusal, voluntary member leave, final closure and rejection of an old invitation. T11 owns the full accepted handover/claim flow. |
| Honest UI | Shared Expo screen supports creation, invitation links/codes, acceptance, revocation, members and explicit removal confirmation. It explains separate roles, unchanged billing/content and the inability to recall downloaded exports. | Chromium/WebKit journeys and a narrow viewport check. Network failure retains the typed address and does not claim success. |

Invitation lifetime is seven days, a bounded implementation choice for the specification's expiring-invitation requirement. The sender copies and shares the link; the UI explicitly says no invitation email has been sent. The token lives in a URL fragment and is submitted in the authenticated POST body, not a query string. It survives navigation through sign-in. Native clients can paste the link/code; no universal-link domain or store identity was introduced.

The initial test suite established the missing membership implementation. The first implementation exposed a removal-result bug: D1 `meta.changes` included trigger writes. Removal now uses returned member rows. Browser tests exposed a stale-startup-URL bug in React Native Web's `Linking.getInitialURL`; web fragment handling now uses current location and `hashchange`. Both regressions are covered and the lessons are recorded in the relevant application guidance.

Browser logs are generated under ignored `test-results/household-web.json` and `test-results/auth-web.json`. Code/tests and the source fingerprint record in [t10.json](t10.json) are the reproducible evidence; transient browser output is not required to run the suite.

## Contracts for following tasks and limits

- `apps/api/src/households/membership.ts` owns membership mutations and the private-read boundary; `routes.ts` resolves identity using the existing Better Auth session on every request. Writes also recheck membership inside SQL. Account authentication alone does not grant household access.
- `contract.ts` is the shared API/UI household shape. The application route is `/household-start`, linked from `/sign-in`. Test-only mailbox/reset controls stay in the local T07 harness; they are not part of the main Worker entry point.
- The main Worker composes the authenticated routes only when `AUTH_BASE_URL`, `BETTER_AUTH_SECRET` and `RESEND_API_KEY` are configured. The existing restricted T07 recipient policy remains in place. The local mailbox uses synthetic recipients and requires no real email delivery.
- Recipe/object product endpoints are not implemented by T10. Their authorization boundary is exercised with private-resource callbacks, including the removal/read race; T12/T15 and later endpoint owners must connect the guard to their actual resources and derive household IDs from server-owned records. This is not evidence of a finished recipe or object-serving feature. Existing D1 job and shopping mutation boundaries are exercised directly.
- T11 must implement the accepted reauthenticated, recipient-accepted handover and orphaned-administration claim flow. T10 deliberately refuses abandonment while other members remain; it does not silently auto-promote a member.
- T03 still needs physical iOS/Android offline persistence tests. T10's native evidence is a shared screen, native session-header integration and successful platform exports, not a newly executed native-device journey or a substitute for T03.
- T09 retains observed photo/audio source-fidelity failures and missing third short recording, five-minute narration and complete human references. No model evaluation or capture acceptance was changed by T10.
- The broader accessibility, integrated isolation/native journey and readiness tasks remain open. No pilot, production rollout or paid access is authorized by this report.
