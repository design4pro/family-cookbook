## Contract and implementation

`applyCheck(db, operation)` accepts an explicit desired state, expected revision and stable operation ID. The authenticated member identity is supplied by the caller. The proof includes minimal membership, active-list, item and outcome tables; it does not implement authentication or household management.

One D1 batch performs a conditional item UPDATE, an INSERT of its durable outcome, then a SELECT of that outcome. The UPDATE checks current membership, household/list ownership, active list, deletion, expected revision and operation deduplication. The INSERT immediately follows the UPDATE and uses `changes()` to distinguish a mutation from a zero-row conflict. The composite operation key is `(household_id, member_id, operation_id)`. Replay preserves the original snapshot, including rejected outcomes; reusing that key with different intent is rejected. Membership removal denies both new writes and replay reads.

Unavailable items return no item state. Stale operations do not rebase. A new deliberate operation may act on the refreshed revision. Check/uncheck has no allowance cost and contains no quota write. The reservation sentinel demonstrates non-interference only; actual queue reservation/settlement belongs to T05.

The simpler separate UPDATE and INSERT calls were rejected because a failure between them could commit only the mutation. A plain atomic batch with an unconditional success INSERT was rejected because zero affected rows do not abort the transaction. No Durable Object or interactive transaction is needed for the demonstrated invariant.

## Reproduction

1. Install with `pnpm install --frozen-lockfile` using Node 24 or a compatible newer runtime.
2. Run `WRANGLER_SEND_METRICS=false pnpm check`. The focused test command forwards file filters and Vitest options.
3. Run `node apps/api/scripts/prepare-remote-proof.mjs > /tmp/family-cookbook-t01-remote.json`.
4. Read its `code` field and execute it through the authenticated Cloudflare connector for account `6cfdf3b5143cddc631383a4c14736c3a`. The generator reads the actual core and migration, emits their hashes, and uses an adapter for the D1 REST batch endpoint. It does not obtain or export credentials.
5. Save the returned JSON as a new evidence run. Existing synthetic rows are preserved; new UUIDs avoid collisions. Reuse assumes the original proof schema remains installed; a changed migration requires a separately verified test database/schema before rerunning.

## Limits and review

The remote proof executes the exact core's SQL via the D1 REST batch API. The binding API is exercised locally in workerd. No deployed Worker HTTP/auth flow, physical database-server crash, replica behavior, native persistence, real family data or quota settlement is claimed. The lost-response test discards a committed result; the crash-boundary test injects a transactional statement failure rather than terminating Cloudflare infrastructure.

Self-review checked the T01 acceptance criteria, tenant predicates, operation-key scope, immutable replay, zero-row semantics, rollback and absence of quota writes. The production integration must preserve these conditions, obtain `memberId` from a verified session, and define operation-record retention with the later lifecycle/deletion tasks. No blocker was found within this proof scope. Both release gates remain closed.
