## Implemented contract

- `apps/app/src/shopping/pending-store.ts`: SQLite transactions partition rows by account, household, immutable list and item ID. The promise resolves only after commit. A single queue serializes reads/writes; failed writes do not poison subsequent work.
- `pending.native.ts`: Expo SQLite file-backed database, WAL, full synchronous mode, one connection owner. The shared module has a different basename to avoid Metro resolving an adapter import back to itself.
- `sync-state.ts`: explicit identity activation, captured scope and abort signal, generation checks before dispatch and after responses. Logout fences immediately and clears all household queues for that account; revocation clears only the affected household. Captured credentials and server-side authorization remain mandatory integration work in T07/T24.
- Unsent taps replace only `next`. Claim persists `flight` before transport and retries the same operation after an unknown outcome. Later intent remains separate. Terminal acknowledgments match the in-flight operation ID. Snapshots preserve pending intent. Stale intent is never silently rebased.
- Removed-item outcomes retain a tombstone so an old cached snapshot cannot recreate that item. Conflicts retain the server state and show a notice. Forbidden outcomes stop the sync loop.
- `proof-shopping.tsx`: temporary native route, synthetic accounts/households, durable status/count/IDs, actual SQLite error injection, controlled transport outcomes, manual retry and optional active reconnect/focus retry. It renders a saved state only after the storage promise succeeds.

The transport is intentionally a manually controlled fixture. It does not call a remote API, authenticate a user or prove server membership checks. T01 supplies separate D1 evidence. T24 must connect these boundaries to authenticated commands and remove the proof route. `Command.revision` maps to the T01 request's `expectedRevision`; the authenticated account maps to the trusted member identity on the server.

## Automated verification

`pnpm test:app` runs eight desktop SQLite integration scenarios:

1. Commit, close and reopen restores the same desired state and operation ID.
2. Rapid unsent checks collapse, in-flight retry is immutable, and an old acknowledgment cannot remove a newer intent or flight.
3. An account switch during claim prevents dispatch under the new account; logout removes old state.
4. Fetching a newer snapshot preserves pending intent; stale rejection removes rejected state without rebase.
5. A real SQLite trigger failure rejects the action and preserves the last saved state. Failed claim cannot mark an operation sent; recovery works after removing the fault.
6. A lost transport response followed by database reopening retries the same flight and retains the later tap.
7. Revocation during an outstanding response aborts/fences the old session, preserving other household/account partitions.
8. Removed items cannot be recreated by cached data; forbidden stops the loop and prevents further checks.

Red-to-green evidence: the first storage test failed on the missing store, subsequent claim/session/snapshot tests failed on their missing behaviors, and the deleted-item regression initially resolved a check that should have been rejected. The final focused suite passes. Desktop SQLite is supplementary evidence, not Expo native SQLite execution. Source hashes and test counts are recorded in [the local manifest](t03-local.json).

`pnpm check` passed: 32 workerd API tests, 8 app tests, both TypeScript checks, Wrangler dry-run and both native Metro exports. `expo install --check` reports compatible dependencies. CI is configured but has not run on a hosted repository.

## Reproduction and remaining acceptance

From the repository root:

```sh
pnpm install --frozen-lockfile
pnpm test:app tests/shopping/pending.test.ts
pnpm check
pnpm --filter @family-cookbook/app exec expo prebuild
pnpm --filter @family-cookbook/app exec expo run:ios --configuration Release --device
pnpm --filter @family-cookbook/app exec expo run:android --variant release --device
```

Use a local Node.js PATH for CocoaPods/Xcode/Gradle; use Android Studio's JBR 21 if the default JDK is incompatible. Do not publish these proof builds. The generated native directories and build products are ignored; app.json and the lockfile define the reproducible input.

On each physical platform, record device/OS, build hash, operator, timestamps, screenshots and the same pending ID before/after termination:

1. Open the embedded-bundle app as Alice/home-a, keep fixture retry disabled, enable airplane mode and disable Wi-Fi. Tap Check milk. Confirm saved status and one pending operation.
2. Force-close the process. Relaunch while still offline. Confirm checked milk, pending count and identical operation ID before any reconnect.
3. Enable Fail SQLite writes, tap Uncheck milk. Confirm a visible failure, no saved confirmation, and the previous durable state/ID. Disable the fault and retry.
4. Reconnect, enable fixture retry or use manual sync. Hold the acknowledgment, tap Uncheck milk, accept the older command. Confirm the newer intent remains and is claimed with its own ID. Reject it as stale to verify server state/notice and no automatic rebase.
5. During a held response, switch account/household, then log out or reject revoked membership. Confirm old responses cannot affect the new partition and no old operation is dispatched under another account.
6. Repeat unknown-outcome restart: terminate while the fixture acknowledgment is held, reopen, reconnect and compare the in-flight ID. Capture the terminal result separately from local-save evidence.

Physical runs are the remaining hard acceptance gate. A simulator pass cannot replace them. A real network/API/auth end-to-end proof belongs to T24; the current fixture validates the client boundary only.
