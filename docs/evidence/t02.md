## Representation and tradeoffs

Text fragments and original sources are immutable contributions. Each contribution contains a deduplicated set of account dependencies. A new independent fragment starts with its contributor. An edit unions the editor with the previous fragment's dependencies; AI output unions every source/context fragment used by that operation. A later C edit therefore cannot erase B from lineage. One hundred successive edits retain the same three account dependencies rather than expanding a chain of copied snapshots.

The fragment is the deletion unit: for example a title, ingredient entry or instruction step. Mixed A/B/C text in one dependent fragment is removed together; the proof does not attempt unreliable word-level attribution or semantic reconstruction. Independent additions are separate fragments. This deliberately trades granular salvage for traceable deletion while preserving independent work.

Current recipes and historical revisions hold ordered fragment references, not additional untracked text snapshots. Managed source, recovery and processor copies refer to their originating contribution. Managed exports record the complete set of contributions embedded in the archive. A mixed export is deleted as an object; its independent source contributions remain available for a later clean export. Already-downloaded member archives are outside the managed inventory and cannot be recalled.

The simpler last-editor/author-label model was rejected: it loses B when C edits after B, and cannot trace AI output from B's source. Repeated full-text history snapshots were rejected because they duplicate sensitive content and obscure which bytes require erasure.

## Purge contract

`planContributorPurge(inventory, accountId)` is a pure planner over a complete, trusted inventory. It returns:

- Explicit creator-added recipe IDs for the deletion preview.
- Row IDs for contributions, historical revisions, asset copies, managed exports and any empty recipes to delete.
- Exact `(store, key)` object targets, without content payloads.
- Updated surviving recipe manifests, preserving the order of independent fragments.

It removes every contribution whose inherited account set contains the deleting account. It removes historical revisions containing those fragments and revisions whose editor metadata belongs to the account. Empty recipe shells are deleted only when no independent contribution remains, including historical work. A creator's independently surviving recipe remains without transferring the deleted contribution to another author: its creator reference is cleared only after the contribution purge is planned. Creator-added recipes are still listed explicitly in the preview.

Any loss of current fragments changes the recipe to `review-required`. Older instructions are never automatically restored. Removing only historical contributions leaves an independently complete approved current version approved. `assistantRecipeContent` returns no context for drafts, review-required recipes, missing references or cross-recipe references; approved manifests preserve fragment order. This helper checks content eligibility, not session/household authorization.

Missing provenance or unresolved inventory references prevent planning. The planner does not silently treat unknown content as independent. An unknown account and a second purge after successful application produce empty plans. The input inventory is not mutated.

## Executable fixture and observed inventory

The main synthetic fixture contains A's recipe and original image, B's edit and recording, C's edit derived from B, C's independent addition, AI extraction from B's recording, three historical revisions, source/recovery/processor copies, a mixed export and an independent export. A's superseded instruction remains historical and is not restored into the current recipe.

The fixture is stored as individually identified rows in local D1 tables `proof_recipes`, `proof_contributions`, `proof_revisions`, `proof_assets` and `proof_exports`. `proof_objects` holds synthetic object bodies. Tests compute the plan from rows read back from D1, apply row deletions/recipe updates, separately apply object deletions, then inspect the database and object inventory again. This is test-only row storage, not T12's final schema or a mocked D1 API.

The first integration case asserts this post-purge state:

| Area | Removed | Preserved |
| --- | --- | --- |
| Contributions | `b-text`, `b-source`, `c-derived`, `ai-derived` | `a-text`, `a-step`, `a-source`, `c-independent`, `safe-text` |
| Historical revisions | `history-b`, `history-c` | `history-a` |
| Asset rows and object bodies | B's original, recovery and processor copies | A's original, recovery and processor copies |
| Managed exports | `mixed-export` and `mixed-export.zip` | `safe-export` and `safe-export.zip` |
| Shared recipe | Dependent current references | A's recipe identity; ordered current references `a-text`, `c-independent`; status `review-required` |
| Independent recipe | Nothing | Unchanged and eligible for assistant context |

The stored inventory contains no `B_PRIVATE` fixture marker after purge. The remaining object bodies are asserted exactly, including A's image/recovery/processor bodies and independent export. Additional cases prove creator-preview scope, deletion of entirely dependent recipes, preservation of independent C work in a B-created recipe, preservation of historical work when no current text survives, metadata-only history removal, repeated purge, and unknown-account non-interference.

## Integration requirements and limits

T12 must persist immutable fragments and enforce lineage on the server: an edit must include its prior fragment, and AI/copy operations must include every input used. Clients must not supply or reset provenance, and neither changing labels nor explicitly copying a field through a product operation makes dependent content independent. Provenance cannot infer undisclosed external copying from text similarity; the proof assumes trusted and complete input provenance.

T12 must preserve complete historical and export references until those managed copies are removed. It must keep independent fragments distinct, preserve current ordering, retain the review-required state until explicit approval and add the actual revision/conflict controls. The proof does not implement saving, approval or a public retrieval endpoint.

T35 must connect the plan to an authoritative deletion workflow: revoke access, freeze/recheck affected writes, reject stale previews, enumerate every real copy, revoke export access, execute idempotent object/processor deletion and confirm completion. The fixture executor is test-only and must not be used as the production purge worker. It intentionally does not claim atomicity across D1 and object stores, protection against concurrent/late jobs, processor acknowledgments or retention deadlines. T05/T06/T35/T38 retain those obligations.

No real R2 or processor bytes were deleted, no account lifecycle was deployed and neither readiness gate has passed. The current proof demonstrates that the representation can identify and remove the required fixture data while preserving independent content. Self-review found no blocker within that scope. The first architectural checkpoint still requires T03.
