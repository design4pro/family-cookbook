## Implemented behavior

| Acceptance boundary | Implementation | Evidence |
| --- | --- | --- |
| Explicit reauthentication | Administrator requests a new code for the server-resolved session email. The existing Better Auth handler provides hashed OTP storage, expiry, attempt limits, rate limits and atomic consumption. A successful verification grants one nomination for five minutes, bound to this session and household. | API tests reject missing proof, wrong/expired/reused OTP, client-supplied identity, another session's proof, revoked sessions and expired grants. Successful nomination consumes its grant. |
| One current-member nominee | A household has at most one pending request. Recipient must be a different, verified current member. An expired request is removed when a new valid request is attempted. | Competing nominations yield one winner; self, outsider and unverified targets are rejected. |
| Recipient acceptance | Request expires after seven days. Only the designated current member can accept while the sender is still administrator and a member. Role update and notifications share one D1 commit. The previous administrator remains a member. | Wrong recipient and repeat acceptance fail; exact expiry fails; successful acceptance preserves all three memberships. |
| Revocation | Sender can cancel. Leaving, removal or profile deletion of either party invalidates pending requests. Old administrative grants and invitation links are invalidated when the role changes. | Cancellation/acceptance race produces one winner. Recipient leave/removal/deletion and rejoin cannot revive a request. Old administrator invitations remain revoked. |
| Separate payment and authorship | Handover writes administration state, requests/grants, notices and obsolete invitation state. It does not relabel recipe authors or modify purchases, payer designation, sources or allowance history. | Source, quota, payer and purchase-intent rows are unchanged. The old administrator remains visibly the payer, loses administrative controls and can leave separately. Existing contribution-deletion regressions pass. |
| Administrator profile deletion | A database trigger captures eligible remaining members before deleting membership and clearing the administrator. Existing members retain household access. Pending invitations cannot claim. No automatic promotion occurs. | Deletion leaves two members and no administrator. Administrative actions are unavailable until an explicit claim. Pending invitees, unverified members and later/rejoined members are rejected. |
| Atomic successor claim | Claim requires a deletion-created eligibility record, current verified membership, an open household and no current administrator. One conditional update wins. | Concurrent claims have one winner. Inactivity does not enable a claim. An empty household closes without any public claim path. |
| Notifications | Durable per-member in-app notices are committed with role changes. Nomination notifies its recipient; deletion and role changes notify remaining members. Notices are visible on the household screen after load/refresh. | All remaining members receive one change notice; browser reload preserves notices. Injected notification-write failure rolls back the role change and leaves the request retryable; successful retry emits notices once. |

The shared Expo administration panel lives inside the existing `/household-start` screen rather than adding a second member-management route. It shows the pending recipient/expiry, cancellation, recipient acceptance and eligible-member claim. Administrator, ordinary member and payer-only views were exercised in both browsers. Labels explain that billing, authorship and allowances do not transfer.

The notification channel is in-app; this task does not claim email or push delivery of role-change notices. OTP emails remain a separate authentication mechanism. The approved recipient restriction remains in place, and the mail template now identifies administration verification separately from sign-in. The public auth wrapper still excludes general email-verification endpoints; only the authenticated administrator route invokes them internally with a server-owned email address.

## T10-T11 contract review and handoff

- Membership, administration, payer identity and contribution provenance remain separate. The T10 private-read guard and D1 mutation membership predicates remain mandatory for future resource endpoints. Both completed identity tasks were reviewed together after this second slice.
- Reauthentication is a short-lived, single-use server grant; a client flag or cached session is never evidence of reauthentication. Keep Better Auth's HTTP handler in the internal OTP flow so its database rate limits and atomic OTP consumption apply.
- Role transitions use conditional D1 updates and `RETURNING`. Triggers make request invalidation and notification persistence part of the same transaction. An unsuccessful notification insert cannot leave a reported successful transition.
- T34/T35 must preserve the profile-deletion transition in migration `0006`: capture pre-existing eligibility before clearing the administrator, remove membership, invalidate pending work/requests and preserve an explicit claim path. Do not replace it with a bare `administrator_id = NULL`, which deliberately grants nobody claim rights. Account deletion still requires the full content/billing/purge workflow; the local test-only `/__proof/delete-profile` endpoint is not a product deletion implementation and must never be deployed.
- T12 must continue deriving authorship/provenance from contributors, never the current administrator. T33 must keep purchase replacement explicit; administration does not move payer designation or subscription ownership.
- Notifications contain generic event kinds, household/member IDs and timestamps, not deleted users' names, emails or content. Membership removal removes that recipient's notices. Later deletion/retention and operational tasks must include these records in their inventory.
- Native evidence for this slice is the shared UI and successful iOS/Android exports, not a new physical-device or simulator UI run. Broader native/accessibility journeys remain their own tasks.

T03 still lacks physical iOS/Android persistence evidence. T09 still has source-fidelity failures and is missing the third short recording, five-minute narration and complete human references. No capture acceptance or native persistence requirement was relaxed. Neither release gate has passed.
